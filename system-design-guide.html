Foundations

What is system design?

System design means deciding how a system is built before it is built: its parts, the boundaries between them, how they talk to each other, and how it meets its requirements for speed, reliability and cost. The output is a blueprint that shows the flow of work through the system.

System design concepts

Horizontal and vertical scaling

Vertical scaling is the process of adding more nodes (servers or instances) to a system to distribute the load and increase its capacity. This approach improves system performance and reliability by allowing it to handle more requests simultaneously. Horizontal scaling is often used in cloud environments and can be achieved through load balancing or sharding (splitting a software system into a few instances, each holding part of the data).

Horizontal scaling involves adding more resources (CPU, memory, storage) to an existing node or server, thus increasing its capacity to handle a higher workload. This can be achieved by upgrading the hardware or allocating more resources in a virtualized environment. Vertical scaling has limitations due to hardware constraints and can result in downtime during the scaling process.

Redundancy and replication

Redundancy means keeping a spare of an important component so the system survives a failure. Replication means keeping several synchronized copies of data on different nodes. Both support availability, fault tolerance and durability when hardware fails or the network splits.

Microservices architecture

A microservices system splits one large application into small services. Each service owns one business capability, has its own data, and talks to others through APIs. Teams can build, deploy and scale each service on its own, at the cost of more operational work.

CAP theorem

Also called Brewer's theorem, CAP says a distributed system cannot guarantee all three of these at once during a network partition:

  • Consistency: every node returns the same, latest data.
  • Availability: every request gets a response.
  • Partition tolerance: the system keeps working when messages between nodes are lost.

Since partitions happen in real networks, the practical choice is between consistency and availability when a partition occurs.

Proxy servers

A proxy sits between clients and servers and forwards requests. Because every request passes through it, it can balance load, cache responses, filter malicious traffic and hide the backend's details.

Message queues

A message queue lets one component send work to another without waiting for it. The producer writes messages into the queue, and the consumer reads them when it is ready. This decouples the two parts, smooths out spikes in load and helps the system survive a consumer that is temporarily down.

File systems

A file system organizes data on storage media into files and directories, enforces access rules and keeps the data intact. A local file system lives on one device. A distributed file system spreads files across many machines, which adds capacity and fault tolerance but makes consistency and performance harder.

Architecture and patterns

Two-phase commit (2PC)

2PC is a protocol that makes a transaction across several resources atomic: either every participant commits or none does. A coordinator runs two phases:

  • Prepare: each participant checks it can commit and votes yes or no.
  • Commit: if all voted yes, the coordinator tells everyone to commit; otherwise everyone aborts.

It is strongly consistent, but participants can block while waiting on the coordinator, which is why it is avoided in many large systems.

Replicated load-balanced services (RLBS)

RLBS runs several identical copies of a service behind a load balancer. The balancer spreads requests across them, so no single copy gets overloaded, and if one copy fails the others keep serving.

Command and Query Responsibility Segregation (CQRS)

CQRS separates writes (commands that change state) from reads (queries that return data). Because the two sides are separate, each can use its own data model and store, and each can scale on its own. Reads are often served from a store shaped for display, which is updated from the write side.

Saga

A saga handles a long-running business transaction across services without a global lock. It is a sequence of local transactions, and each one has a compensating action that undoes it. If a step fails, the compensations run in reverse order. The saga gives up strict isolation to keep services available and fast.

Example: placing an order touches three services, so each step has a matching undo.

  • Order service creates and reserves the order; compensation cancels it.
  • Inventory service reserves stock; compensation releases it.
  • Payment service charges the customer; compensation refunds.

Sharded services

Sharding splits data across several instances by a key, such as a user ID. Each shard holds a slice of the data and handles its share of traffic, so capacity grows by adding shards. The trade-offs are harder queries across shards, rebalancing when shards are added, and more complicated consistency.

System design examples

eCommerce system

An online store needs a browsing front end, a cart, payments, order management and a warehouse system. These parts must exchange data reliably while handling traffic spikes, protecting customer data and staying available.

CAP view

Prioritized: consistency and availability.

  • Consistency for inventory, payments and orders. Two shoppers must not buy the last unit, and a payment must not be recorded twice. Checkout can refuse to proceed if it cannot confirm stock.
  • Availability for browsing and the cart. A store that will not load during a sale loses revenue, and a product page a few seconds old causes no harm.

Deprioritized: partition tolerance as a choice. A store runs across many services and networks, so partitions will happen. You plan for them rather than choose them. For example, checkout pauses and retries when the warehouse is unreachable.

Content delivery network (CDN)

A CDN keeps copies of content such as images, video and pages on servers near users. A request is served from the nearest edge, which lowers latency and takes load off the origin. The design must handle cache freshness, routing to the best edge, failover and secure delivery.

CAP view

Prioritized: availability and partition tolerance.

  • Availability: a user must get a file from the nearest edge. A page that fails to load is worse than one that is slightly out of date.
  • Partition tolerance: edges are spread around the world and will sometimes lose contact with the origin. They keep serving cached copies instead of going dark.

Deprioritized: consistency. A cached copy can lag the origin for as long as its time-to-live. That is fine for images and video. For content that must change immediately, use a purge request or a shorter time-to-live.

Social networking platform

A social platform is a set of subsystems: sign-in, profiles, messaging, the news feed, media storage and search. The feed has to be assembled quickly from many users' activity, and the whole system has to handle huge read and write volumes as the user base grows.

CAP view

Prioritized: availability and partition tolerance.

  • Availability: the feed and profiles must load for everyone, even during a regional outage.
  • Partition tolerance: data lives in several regions, so parts of the network will sometimes be cut off from each other. Users should keep getting a feed, even if some of it is stale.

Deprioritized: strict consistency. Like counts, follower counts and feed ordering can converge over a few seconds, and nobody is harmed by that. Privacy settings and blocks are the exception: they must take effect quickly and reliably, so route them through a stronger path.

Internet of Things (IoT) system

An IoT system has many small devices, such as sensors and actuators, that send readings through gateways to a cloud back end. The design must cover device onboarding and management, secure communication, processing large streams of data, and scaling to very large device counts.

CAP view

Prioritized: partition tolerance and availability.

  • Partition tolerance is the normal case here, not a rare failure. Devices lose signal, run out of battery or sit behind unreliable links, so the design must expect disconnection.
  • Availability: the gateway accepts and buffers readings when the cloud cannot be reached, so data is not dropped.

Deprioritized: consistency. Sensor readings are a stream. A late, duplicated or slightly out-of-order reading can be sorted out by timestamp later. Commands such as shutting off a valve or pushing firmware need stronger guarantees, so handle them on a separate path.

Tools and techniques

Data flow diagrams (DFD)

A DFD shows how data moves: processes transform it, external entities send and receive it, and data stores hold it. Drawing one makes bottlenecks and unclear responsibilities easy to see during analysis and design.

Architecture diagrams

Architecture diagrams show the structure of a system and how its parts depend on one another. They help stakeholders and engineers agree on the design and spot issues early. Keeping them current with the code is the hard part.

Data dictionaries

A data dictionary documents every data element: its name, type, length, default, meaning and relationships. It keeps the team's definitions consistent and is the reference for the data model and the storage design.

Decision trees

A decision tree shows a choice as branches: each node asks a question, each branch is an answer, and each leaf is an outcome. Trees are good for working through complicated logic and explaining it to others.

Decision tables

A decision table lays out conditions and the actions they lead to, one rule per row. It makes it easy to check that every combination is covered, and that no two rules contradict each other.

Pseudocode

Pseudocode describes an algorithm in plain structure without tying it to a language's syntax. It is used to discuss logic with the team and as a starting point for real code.

Unified Modeling Language (UML)

UML is a standard set of diagrams for describing software. Structure is shown with class diagrams, behavior with state and activity diagrams, and interactions with sequence diagrams. A shared notation makes design discussions and handoffs clearer.

APIs and contracts

An API is the set of rules and operations one component exposes to others, so they can work together without knowing each other's internals. A contract is a precise, checkable description of what the API accepts and returns, and of the behavior callers can rely on. Contracts let teams change internals safely and catch breaking changes early.
