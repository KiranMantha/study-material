Basics

What Kafka is

Kafka is a distributed event streaming platform. Producers write events to it, and consumers read those events, often at a different time and rate. Underneath, it is a set of append-only logs spread across a cluster of servers called brokers. Because the data is kept in a log rather than deleted on read, many independent consumers can read the same events.

Topics, partitions and offsets

A topic is a named stream of events, such as orders or page-views. Each topic is split into one or more partitions. A partition is an ordered, append-only log. Each record in it gets a sequential number called an offset, which is its position in that partition. Offsets are unique only within a partition.

A record contains a key (optional), a value, a timestamp and optional headers. The key affects which partition the record goes to, covered in the next section.

Keys and ordering

Kafka guarantees order within a partition only. There is no global order across the whole topic. When a record has a key, Kafka hashes the key and uses the result to choose a partition. So all records with the same key land in the same partition and stay in order. Records without a key are spread across partitions.

Interview lens: Expect "how do you pick a partition key?" Name the ordering requirement first, then the spread: a key with few values or one very busy value creates hot partitions.

Cluster and reliability

Brokers and replication

A broker is a Kafka server. Each partition is stored on several brokers based on its replication factor, often 3. One replica is the leader and handles all reads and writes for that partition. The others are followers that copy the leader's data. The followers that are fully caught up form the in-sync replica set (ISR). If a leader fails, a new leader is chosen from the ISR, so committed data is not lost.

Producer acknowledgements

The producer's acks setting controls how long it waits before treating a write as successful. This is the main trade-off between speed and durability:

  • acks=0: the producer does not wait. Fastest, but records can be lost silently.
  • acks=1: the leader confirms after writing to its own log. A leader failure before replication can still lose the record.
  • acks=all: the leader confirms after every in-sync replica has the record. Combined with min.insync.replicas, this is the setting for data you cannot lose.
Interview lens: Always state the durability choice and its cost in one sentence: "acks=all with min.insync.replicas=2 and replication factor 3, so one broker can fail without losing acknowledged writes, at the cost of added write latency."

Consuming

Consumer groups

A consumer group is a set of consumers that share the work of reading a topic. Within a group, each partition is assigned to at most one consumer at a time. That is how Kafka scales reading: the maximum parallelism of a group equals the number of partitions. Consumers in a group beyond that number sit idle. Different groups read the same topic independently, and each group keeps its own position.

Interview lens: The partition count is the ceiling on parallelism. If the interviewer asks you to scale a consumer that is already at that ceiling, the answer is more partitions (with a plan for the key remapping), not more consumers.

Offsets and commits

A consumer tracks its position in each partition using offsets. After processing records, it commits the offset to Kafka, which stores committed offsets in an internal topic. If the consumer restarts, it resumes from the last committed offset. Anything read but not yet committed is read again.

Commits can be automatic (on a timer, which can commit before processing finishes) or manual (after your code succeeds). Choosing when to commit decides what happens during a crash.

Delivery guarantees

The order of "process" and "commit" decides how a crash is handled. There are three standard guarantees:

  • At-most-once: commit first, then process. A crash after the commit loses that record. No duplicates, but possible loss.
  • At-least-once: process first, then commit. A crash before the commit repeats the record. No loss, but duplicates are possible, so make processing idempotent.
  • Exactly-once: Kafka transactions combine the output writes and the offset commit into one atomic step. Consumers read with read_committed to skip aborted writes. This works inside Kafka. Writes to outside systems still need idempotent handling or a transactional sink.
Interview lens: Do not answer "exactly-once" without qualification. Say what is exactly-once (Kafka-to-Kafka with transactions) and what still needs idempotent handling (databases, emails, payments). Interviewers listen for that boundary.

Storage and operations

Retention and compaction

Kafka does not delete records when they are read. Records are removed by a policy:

  • Time or size retention (retention.ms, retention.bytes): old segments are deleted after a period or once the log exceeds a size.
  • Log compaction: for each key, Kafka keeps only the latest value. A record with a null value (a tombstone) deletes the key after a delay. This suits changelogs and current-state data, such as the latest profile for each user.

Rebalancing

When a consumer joins or leaves a group, or stops responding, Kafka reassigns partitions among the remaining consumers. This is a rebalance. Older protocols stop every consumer while partitions move (eager rebalancing). The cooperative protocol moves only the partitions that need to change, so most consumers keep working.

Metadata: KRaft

Kafka must track which brokers are alive, who leads each partition and the topic configuration. Earlier versions used Apache ZooKeeper for this. Current Kafka uses KRaft, where a quorum of controller nodes stores the metadata in a Kafka log of its own. This removes an external dependency and makes large clusters faster to recover. ZooKeeper support was removed in Kafka 4.0.

Ecosystem

Kafka Connect and Kafka Streams

Kafka Connect moves data between Kafka and other systems without custom code. A source connector reads from a database or service into Kafka. A sink connector writes from Kafka into a warehouse, search index or storage. Kafka Streams is a client library for processing topics: filtering, joining, aggregating and windowing, with state kept in local stores that are backed up to Kafka.

Operating Kafka

Consumer lag and common pitfalls

Consumer lag is the difference between the newest offset in a partition and the consumer group's committed offset. Growing lag means consumers are falling behind. It is the most useful health signal for a Kafka pipeline.

Common pitfalls:

  • Too few partitions caps consumer parallelism. Adding partitions later changes which partition a key maps to, which can break key ordering for existing data.
  • Hot keys: one very busy key sends most traffic to one partition. Pick keys with a more even spread.
  • Too many partitions add overhead to brokers and slow recovery after failures.
  • Long processing inside the poll loop can exceed the consumer timeout, which triggers a rebalance.
  • Losing data with acks=1 or a small ISR: use acks=all with a suitable min.insync.replicas for important topics.
Interview lens: Treat lag as the first monitoring signal you would name. Follow it with the likely causes in order: slow processing, a hot partition, frequent rebalances, then broker or network trouble.

Interview perspective

Kafka in FANG-style interviews

In a system design round, Kafka usually appears as the event backbone for a feed, analytics pipeline, notification system or payment event stream. Interviewers are less interested in the API and more in whether you can size the cluster, pick the right keys, and explain what happens when things fail. The points below are a common structure, not an official rubric.

1. Justify the choice

State why Kafka fits: high throughput, a replayable log, several independent consumers, and retention long enough for reprocessing. Mention the alternative you rejected and why. For example, a plain task queue deletes a message once it is consumed, which rules it out when several systems need the same events.

2. Size partitions and storage

Work from the numbers, as in the estimation section of the interview prep page. The partition count needs to satisfy two constraints: throughput and consumer parallelism. Add headroom, because increasing partitions later changes key mapping.

3. Walk through failures

Interviewers often ask "what breaks?" Prepare short answers for these cases:

  • Broker failure: leadership moves to an in-sync follower. With acks=all and a replication factor of 3, acknowledged writes survive.
  • Consumer crash: its partitions are reassigned, and processing resumes from the last committed offset. Some records may be reprocessed, so the handler must be idempotent.
  • Poison message: a record that always fails stalls its partition. Use retries with backoff, then a dead-letter topic, and alert on it.
  • Out-of-order events: ordering holds only within a partition. Use event timestamps or sequence numbers in the handler where cross-key order matters.
  • Schema change: producers and consumers evolve at different times. Use a schema registry with compatibility rules, so old and new readers can coexist.
  • Region failure: cross-region replication (such as MirrorMaker 2 or a managed equivalent) lets consumers in another region take over, with a lag and a possible gap. State the recovery point you accept.

4. Answer template

For any "design X with Kafka" question, use this order: the event shape and key, the topic and partition count with the sizing reason, the producer durability setting, the consumer groups and what each does, the delivery guarantee and idempotency plan, the retention and reprocessing story, and the monitoring signals (lag, error rate, DLQ depth).

5. Likely follow-ups

  • "How would you reprocess last month's events?" Use retention or an archive in object storage, then replay into a new consumer group so the live group is not disturbed.
  • "What if one customer produces 80% of the traffic?" Discuss a hot-key remedy: a sub-key or salt for that customer, or a dedicated topic.
  • "How do you keep ordering for a user's actions while scaling?" Key by user ID so each user's events share a partition, and accept that global order is not kept.
  • "Why not store everything in the database and skip Kafka?" The answer is decoupling, fan-out to several consumers, and replay. Name the cost: an extra system to run and operate.

Reference

Quick reference

  • Topic: named stream, split into partitions.
  • Partition: ordered, append-only log. The unit of parallelism and of ordering.
  • Offset: position of a record within one partition.
  • Broker: a Kafka server that stores partition replicas.
  • Leader / follower / ISR: the replica that serves reads and writes, the copies, and the caught-up copies eligible for leadership.
  • Consumer group: consumers that share a topic; one consumer per partition at a time.
  • acks: 0, 1 or all. Trade speed against durability.
  • Idempotent producer (enable.idempotence=true): retries do not create duplicate records in a partition.
  • Retention / compaction: time or size limits, or keep only the latest value per key.
  • KRaft: built-in metadata quorum that replaces ZooKeeper.
