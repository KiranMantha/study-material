Storage

Log segments and index files

Each partition is a directory on a broker's disk, named topic-partition. Inside are segments: files that hold a contiguous range of offsets. A segment's file name is its base offset, zero-padded to 20 digits. Only the newest segment, the active one, accepts writes. Older segments are immutable, which makes deletion and compaction simple.

  • .log: the record batches themselves.
  • .index: a sparse map from offset to byte position in the .log. An entry is written about every log.index.interval.bytes (4 KB by default).
  • .timeindex: a sparse map from timestamp to offset, used for "give me the first record after time T".
  • .snapshot files: producer state for idempotence and transactions. leader-epoch-checkpoint records where each leader epoch started.
Interview lens: This design explains why Kafka keeps up with heavy writes and reads. Writes are sequential appends, reads are mostly sequential scans, and the index stays small enough to keep in memory.

Sources: Docs: Persistence (log and index files) not read

Record batches and compression

Producers send records in batches, and the broker stores batches as they arrive. The batch header carries what the broker needs for offsets, leader epochs, checksums, transactions and idempotence. Compression applies to the whole batch, so compressing larger batches compresses better.

The broker usually stores batches exactly as received and avoids decompressing them. It has to decompress only when it must validate or convert the batch, or when the topic's compression.type differs from the producer's. That is why end-to-end compression works well on the broker side.

Sources: Docs: Message format not read · KIP-98 checked

Reads: page cache and zero-copy

Kafka does not keep its own large in-memory cache of records. It relies on the operating system's page cache. Recent writes are usually still in memory, so consumers that read near the end of the log are served from RAM. For consumers that read further back, the broker uses sendfile, which moves bytes from the page cache to the network socket inside the kernel, skipping the copy into broker user space.

Sources: Docs: Persistence (page cache and file system) not read

Producing

Producer internals

When your code calls send(), the producer does not send anything right away. It serializes the record, chooses a partition, and appends it to a record accumulator, which holds one queue of batches per partition. A background sender thread drains ready batches, groups them by broker, and sends them. A batch is ready when it is full (batch.size) or its wait has reached linger.ms.

  • Blocking: when buffer.memory is full, send() blocks for up to max.block.ms, then throws. A slow broker shows up first as blocked producers.
  • Throughput levers: larger batch.size, a small non-zero linger.ms, and compression. Each one trades a little latency for much better throughput.
  • In-flight requests: max.in.flight.requests.per.connection limits unacknowledged requests per broker connection. With retries enabled and idempotence off, a value above 1 can reorder records.
  • Time budget: delivery.timeout.ms is the total time from send() to success or failure, including retries and waiting in the accumulator. request.timeout.ms applies to one request.
Interview lens: If asked how to raise throughput without losing data, mention batching, linger.ms, compression and async sends with a callback. Note that the callback is where failures show up, not the return from send().

Sources: Docs: Producer configs not read · Docs: Producer API not read

Partitioner and key hashing

For a record with a key, the default partitioner hashes the serialized key (murmur2) and takes it modulo the partition count. Two consequences matter. Equal keys always map to the same partition while the count stays the same. Changing the partition count remaps keys, so ordering for existing keys can break across the change.

Records without a key use a sticky partitioner. The producer fills one partition's batch, then switches to another. This gives bigger batches and fewer requests than random placement. A custom partitioner can implement any rule, such as routing a known hot key to a dedicated partition.

Sources: Docs: Producer configs (partitioner.class) not read · KIP-480 sticky partitioner, from memory

Idempotent producer

With enable.idempotence=true, the broker assigns the producer a producer ID and an epoch. Each batch carries a per-partition sequence number. The broker remembers the latest sequence numbers per producer and partition. A retried batch that it has already stored is recognized and dropped, and the producer gets the original acknowledgement. A batch that arrives out of order is rejected.

Idempotence covers duplicates from producer retries within one session of a producer. It does not cover duplicates from your application calling send() twice. The epoch also fences old instances: when a new instance starts with the same transactional.id, the broker rejects the old one.

Sources: KIP-98 checked · Docs: Delivery semantics not read

Replication and the control plane

Replicas, fetches and the high watermark

Followers replicate by fetching from the leader, using the same fetch protocol as consumers. The leader tracks each follower's log end offset (LEO), which is the next offset that replica will write. The high watermark (HW) is the smallest LEO among the in-sync replicas. Offsets below the HW are committed. Consumers can read only up to the HW.

Sources: Docs: Replication not read

Leader epochs and log truncation

Every leadership change starts a new leader epoch. The leader records the offset where each epoch began. When a former leader comes back as a follower, it must discard any records that the new leader never received. Earlier versions decided this using the high watermark, which could cause data loss or divergent logs in some failure sequences. The fix (KIP-101) is to ask the new leader which offset ends the old epoch, then truncate to that point.

Sources: KIP-101 checked · KIP-279 checked

Leader election, ISR and unclean election

The ISR is the set of replicas that are caught up. A follower falls out of the ISR when it has not caught up within replica.lag.time.max.ms, and it rejoins once it catches up. When a leader fails, the controller elects a new leader from the ISR. That is the safe path: every replica it chooses holds all committed records.

  • Clean election: a new leader comes from the ISR. No committed data is lost.
  • No ISR member available: with unclean.leader.election.enable=false, the partition stays offline until an ISR member returns. Availability is sacrificed to protect data.
  • Unclean election: with it set to true, an out-of-sync replica can become leader. The partition comes back sooner, but records that the old leader had acknowledged, and that no other replica copied, are lost.
  • min.insync.replicas: with acks=all, a write fails if the ISR has fewer members than this value. That protects durability when replicas are down, and it causes the producer errors you see during outages.
Interview lens: The durable setup is replication factor 3, min.insync.replicas=2, acks=all, and unclean election off. Be ready to explain the trade: one broker can fail without losing acknowledged writes, but two failures make the partition reject writes rather than risk data.

Sources: Docs: Replication (ISR, unclean election) not read · Docs: Broker configs not read

KRaft: controllers and the metadata log

Cluster metadata includes topics, partition assignments, leaders, ISRs, configs and ACLs. In KRaft mode, a set of controller nodes forms a Raft quorum. The active controller appends metadata changes to an internal log, __cluster_metadata. Brokers fetch that log and apply it locally. A new active controller is elected by Raft if the current one fails. Snapshots keep the log from growing without limit. Kafka 4.0 removed the older ZooKeeper-based mode.

Sources: Docs: KRaft not read · KIP-500 and KIP-595 (KIP-595 not found in search), from memory

Consuming

Group coordinator and offset storage

Each consumer group is managed by one broker, its group coordinator. The coordinator is the leader of the partition of __consumer_offsets that the group ID hashes to. Consumers talk to it for joining, syncing assignments, heartbeats and offset commits. Committed offsets are stored as records in __consumer_offsets, so they are replicated like any other topic.

In the classic protocol, when the group changes, the coordinator asks the members to re-join. One member, the group leader, computes the partition assignment, and the coordinator sends each member its share through the sync step. The newer protocol (KIP-848) moves the assignment to the coordinator and sends incremental changes through heartbeats.

Sources: KIP-848 checked · Docs: Consumer configs not read

Heartbeats and the poll loop

Two independent timers decide whether a consumer is alive. The heartbeat thread sends heartbeats every heartbeat.interval.ms. If the coordinator hears nothing for session.timeout.ms, it removes the member. The poll loop is your code calling poll(). If the gap between two poll() calls exceeds max.poll.interval.ms, the consumer leaves the group even though its heartbeats are still arriving. That is the case where slow processing causes rebalances.

  • max.poll.records caps how many records each poll returns. Lowering it shortens each loop when processing is expensive.
  • Long pauses from garbage collection, a blocked thread or a slow downstream call can trigger the same removal as slow processing.

Sources: Docs: Consumer configs (heartbeat, poll timeouts) not read

Rebalance protocols and assignors

A rebalance is triggered by a member joining, leaving or timing out, or by a topic's partition count changing. Protocol differences matter for downtime:

  • Eager: every member gives up all its partitions, then the group reassigns them. Processing stops across the whole group for the duration.
  • Cooperative (incremental): members keep the partitions they already have, and only the partitions that must move are revoked and reassigned, in rounds. Most consumers keep processing.
  • Consumer protocol (KIP-848): an incremental heartbeat-driven protocol where the coordinator computes assignments. It reduces the time the group spends in a rebalance.
Assignor What it does Watch for
RangeAssignor Assigns contiguous partition ranges per topic Can overload the first consumers when several topics have the same partition counts
RoundRobinAssignor Deals partitions out one by one across all topics Moves many partitions on any membership change
StickyAssignor Balances load and keeps existing assignments where possible Eager protocol: stickiness still stops every consumer
CooperativeStickyAssignor Sticky assignment with the cooperative protocol All members must support the cooperative protocol before the upgrade completes
Interview lens: If asked why deploys cause a processing pause, name the eager protocol and then the fix: cooperative assignment, static membership so restarts don't trigger a rebalance, and a session timeout long enough to cover a normal restart.

Static membership: setting group.instance.id makes a restarting consumer reclaim its previous partitions without a rebalance, provided it rejoins within session.timeout.ms. It suits stateful consumers and rolling restarts.

Sources: KIP-429 checked · KIP-848 checked · Docs: Consumer configs (partition.assignment.strategy) not read · KIP-345 static membership, from memory

Consumer fetching and follower fetching

Consumers do not request one record at a time. Each fetch asks for data across partitions, and the broker can hold the request open until enough data is ready. That is long polling, controlled by fetch.min.bytes and fetch.max.wait.ms. Size limits are set per request (fetch.max.bytes) and per partition (max.partition.fetch.bytes).

  • Fetch sessions let a consumer send only the partitions that changed since its last request, which saves work for consumers that read many partitions.
  • Follower fetching (KIP-392): with broker.rack set on brokers and client.rack set on consumers, a consumer reads from the nearest replica. This cuts cross-zone traffic, which is often billed. Reads may be slightly behind the leader.
  • auto.offset.reset applies only when the group has no committed offset or the offset is out of range: earliest, latest, or none, which throws an error.

Sources: KIP-392 checked · Docs: Consumer configs (fetch settings) not read

Transactions

Transactions in detail

A transaction lets a producer write to several partitions and commit the consumer offsets in the same atomic step. Four pieces make it work:

  • Transactional ID: a stable name for a logical producer. It survives restarts, which is how the broker fences the old instance.
  • Transaction coordinator: a broker that tracks the state of each transaction in the internal topic __transaction_state.
  • Control markers: commit or abort records written into each partition the transaction touched.
  • Last stable offset (LSO): the offset below which no transaction is still open. read_committed consumers read only up to the LSO and skip aborted records.
  • Consume-transform-produce: sendOffsetsToTransaction adds the consumer's offset commit to the same transaction, so output and progress move together.
  • Cost: a transaction adds round trips to the coordinator and waits for the markers. Use it for correctness, and expect extra latency compared with plain writes.
  • Scope: exactly-once covers Kafka-to-Kafka work. External systems still need idempotent writes or their own transactions.
  • Timeouts: transaction.timeout.ms aborts a transaction left open by a crashed producer, which allows the LSO to move forward.
Interview lens: Explain the chain in order: transactional ID for fencing, coordinator state for recovery, markers for visibility, LSO for consumers. Naming those four parts shows you know what happens when a crash lands in the middle of a commit.

Sources: KIP-98 checked · Docs: Design (transactional messaging) not read

Ecosystem

Kafka Connect internals

Connect runs workers, which execute connectors. A connector splits its work into tasks, up to tasks.max, and the workers in a cluster share those tasks. Configuration, offsets and status are stored in three internal topics (connect-configs, connect-offsets, connect-status), so a worker can fail and the cluster reassigns its tasks.

  • Errors: errors.tolerance decides whether a bad record stops the task, and errors.deadletterqueue.topic.name sends failed records to a dead-letter topic.
  • Modes: distributed mode runs the cluster you configure through the REST API. Standalone mode runs a single worker, which suits development.

Sources: Docs: Kafka Connect not read

Kafka Streams internals

A Streams application builds a topology of processing steps. Each source partition becomes a task, and tasks run on stream threads. Operations that change the key, such as groupBy, write to an internal repartition topic so that all records for a key reach the same task. Stateful operations keep their data in state stores, usually RocksDB on local disk. Each store is backed by a changelog topic, so a new instance can rebuild the store from Kafka.

  • Standby replicas (num.standby.replicas) keep warm copies of stores, so failover takes less time to rebuild state.
  • Guarantees: processing.guarantee is at-least-once by default. Set exactly_once_v2 for exactly-once processing inside the application.
  • Joins need the topics to be co-partitioned: same key, same partition count. Otherwise the join is wrong or the application refuses to start.
  • Windows (tumbling, hopping, sliding, session) use a grace period for late records. Results inside the window can be suppressed until it closes.

Sources: Docs: Kafka Streams not read

Operations

Retention, compaction and tiered storage

Two cleanup modes apply per topic. Delete removes whole closed segments once they are older than retention.ms or the partition exceeds retention.bytes. Compact keeps the newest record per key within closed segments, and removes a key entirely when it receives a null-value tombstone. The active segment is never deleted or compacted.

Compaction works in the background using a dirty ratio. It runs when the share of uncompacted data crosses min.cleanable.dirty.ratio, and it honours min.compaction.lag.ms and max.compaction.lag.ms so records are not compacted too early or too late. Tombstones are kept for delete.retention.ms so consumers can see the deletion.

Tiered storage (KIP-405) moves closed segments to object storage. Local disks keep the recent data, and the cluster keeps the full history at lower cost. Reads for old offsets fetch from remote storage, which is slower. Relevant settings: remote.storage.enable, local.retention.ms and local.retention.bytes.

Sources: KIP-405 checked (third-party explorer page) · Docs: Log compaction not read

Security and quotas

  • Listeners: each listener has a protocol (PLAINTEXT, SSL, SASL_PLAINTEXT, SASL_SSL). advertised.listeners is what clients are told to connect to. A wrong advertised address is one of the most common connection failures, because clients connect to the bootstrap address and then to whatever the broker advertises.
  • Authentication: TLS for encryption and client certificates, or SASL mechanisms (PLAIN, SCRAM, OAUTHBEARER, GSSAPI/Kerberos).
  • Authorization: ACLs per resource (topic, group, cluster, transactional ID) and operation (read, write, describe, create). KRaft clusters use the StandardAuthorizer.
  • Quotas: limits on producer bytes per second, consumer bytes per second and request-handler time, set per client ID or user. They keep one noisy client from starving others.

Sources: Docs: Security not read

Command-line tools

These ship in the bin/ directory of a Kafka release. Script names can differ by distribution.

  • kafka-topics.sh: create, describe and alter topics, including partition counts and leaders.
  • kafka-consumer-groups.sh --describe --group <name>: per-partition committed offsets, log end offsets and lag. First stop for lag questions.
  • kafka-configs.sh: view and change topic, broker and client configs without a restart where the config is dynamic.
  • kafka-leader-election.sh: trigger preferred leader election after a broker returns.
  • kafka-reassign-partitions.sh: move partition replicas between brokers. For continuous balancing, many teams use Cruise Control.
  • kafka-dump-log.sh: decode segment files to inspect batches, offsets, sequence numbers and timestamps.
  • kafka-console-producer.sh and kafka-console-consumer.sh: quick tests, including reading with --from-beginning or showing keys and headers.
  • kafka-metadata-shell.sh: inspect KRaft metadata when diagnosing controller state.

Sources: Docs: Quickstart and the bin/ tools not read

Interview

Deep-dive interview questions

Each question below is a common follow-up to the basics. Answer in two parts: what happens by default, and what changes when you tune for something else.

  • What exactly is written to disk when a producer sends a batch? The broker validates the batch, assigns offsets, updates the leader epoch and producer state, appends to the active segment, and updates the index. Flushing to disk is left to the OS by default, and durability comes from replication, not fsync.
  • Why can a consumer read a record that the leader just wrote but has not yet been replicated? It cannot, by default. Consumers are capped at the high watermark, so records become visible only after the ISR has them.
  • A broker crashes with acks=1. What can you lose? Records the leader acknowledged but had not replicated. With acks=all and min.insync.replicas=2, acknowledged records exist on at least two replicas.
  • Why does a restarted consumer sometimes reprocess a window of records? Its last commit lags its processing. Use manual commits after processing, make handlers idempotent, or commit inside a transaction with the output.
  • Why would adding a consumer not speed up a group? It is already at the partition ceiling, so the extra consumer sits idle. Add partitions, with a plan for key remapping.
  • How does Kafka handle a very large message? Raise message.max.bytes, max.request.size and the consumer fetch limits together, and check the broker's replica fetch size. Large messages are costly, so a common answer is to store the payload elsewhere and send a reference.
  • Why does an idempotent producer still need a sensible retry budget? Idempotence removes duplicates, but a batch that keeps failing blocks its partition until delivery.timeout.ms expires. A short budget surfaces a real outage sooner.
  • How would you move a partition to a new broker with minimal impact? Use the reassignment tool or Cruise Control, throttle replication so the move does not starve production traffic, and watch the under-replicated count until the move finishes.

Sources: No single source. Answers draw on the sections above.
